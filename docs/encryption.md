# HelixSync Encryption Model

HelixSync uses end-to-end encryption (E2E) by default (`encryptionVersion >= 1`).
Encryption enforcement (`REQUIRE_ENCRYPTION`, enforced server-side, see §7) is
on by default, and production deployments MUST leave it on. Plaintext payloads
(`encryptionVersion: 0`) are supported only for local testing and debugging
with `REQUIRE_ENCRYPTION=false`, and are explicitly **not production-ready**.

This document is normative for both the extension (encrypt/decrypt) and the
server (opaque storage). No implementation may deviate from the primitives
listed here. Do not invent cryptography — only vetted, audited library
implementations of the primitives below may be used:

- Rust: `chacha20poly1305`, `argon2`, `rand_core` (OS CSPRNG via
  `getrandom`/`OsRng`). The server only ever runs these on `authKey` (§2) —
  never on the account password, which it never receives.
- TypeScript/extension and web dashboard: WebCrypto (`crypto.subtle`) for
  HKDF-SHA256 key derivation, plus `@noble/ciphers` (XChaCha20-Poly1305) and
  `@noble/hashes` (Argon2id, CSPRNG) — independently audited, pure-TypeScript
  implementations. Both clients implement the same derive/wrap/unwrap
  primitives (`extension/src/crypto/index.ts`, `web/src/crypto/index.ts`),
  so an account created on one is fully usable from the other.

## 1. Key Hierarchy

```text
Password (never leaves the client, never sent anywhere)
   |
   +-- Argon2id --> Master key (M, never leaves the client)
                       |
                       +-- HKDF "helixsync-auth-v1" --> authKey (sent to the server instead of the password)
                       |
                       +-- HKDF "helixsync-kek-v1"  --> KEK (never leaves the client)
                                                            |
                                                            +-- wraps/unwraps --> Account key (AK)
                                                                                     |
                                                                                     +-- HKDF "helixsync-sdek-v<N>" --> SDEK_v(N), actually encrypts payloads
```

- **Master key (M)**: derived client-side from the account password via
  Argon2id (§2), keyed to a per-account `kdfSalt`. Never leaves the client,
  never sent anywhere — it exists only to derive `authKey` and `KEK`.
- **authKey**: `HKDF-SHA256(M, info="helixsync-auth-v1")`. The *only* secret
  the client ever sends to the server, in place of a password (register,
  login, device registration, password change). The server hashes it with
  its own independent Argon2id salt (`users.password_hash`) for
  authentication, as it would a password, but never sees the password
  itself, or `M`, or `KEK`.
- **KEK (key-encryption key)**: `HKDF-SHA256(M, info="helixsync-kek-v1")`.
  Never leaves the client, never sent anywhere. Used only to wrap/unwrap the
  account key.
- **Account key (AK)**: 32 random bytes (CSPRNG), generated once by whichever
  client registers the account, and never regenerated by an ordinary
  password change (§4). Stored server-side only in its wrapped
  (KEK-encrypted) form — opaque to the server, which cannot unwrap it
  without `KEK`, which it never has. AK — not a password-derived value — is
  the root every `SDEK_v(N)` derives from.
- **SDEK**: the key that actually encrypts operation payloads. `SDEK_v1` is
  derived from AK via HKDF-SHA256 with a per-key-version `info` string
  (`"helixsync-sdek-v" || keyVersion`). Rotation (§4) introduces `SDEK_v2`,
  etc., without needing a new AK.

The server persists, per user: `kdf_salt` (the Argon2id salt for deriving
`M`), `kdf_params` (Argon2id cost, opaque JSON the server never interprets),
`wrapped_account_key` (AK, encrypted under a KEK the server never has), and
`account_key_version`. Never the password, never `M`, never `KEK`, never
plaintext AK — the server cannot derive the encryption key under any of
these fields, even with full database and process access.

## 2. Initial Key Generation

**Registration** (web dashboard only — the extension never creates
accounts, only registers devices on an existing one):

```text
1. Client generates a random kdfSalt and picks kdfParams (the fixed
   constants below).
2. Client derives M = Argon2id(password, kdfSalt, kdfParams), then
   authKey = HKDF(M, "helixsync-auth-v1") and KEK = HKDF(M, "helixsync-kek-v1").
3. Client generates AK (32 random bytes) and wrappedAK = wrap(KEK, AK).
4. Client calls POST /api/v1/auth/register with
   { email, authKey, kdfSalt, kdfParams, wrappedAK } — never the password.
```

**Login (web) / device registration (extension)** — every device after the
first:

```text
1. Client calls POST /api/v1/auth/prelogin { email } to fetch this
   account's kdfSalt/kdfParams (docs/protocol.md §7). An unknown email
   still gets a plausible-looking response, so prelogin can't be used to
   enumerate accounts.
2. Client derives M, authKey, and KEK exactly as at registration.
3. Client calls POST /api/v1/auth/login or POST /api/v1/devices/register
   with { email, authKey } — never the password.
4. The response includes wrappedAK; the client unwraps it locally with KEK
   to recover AK. A wrong password surfaces as a 401 from the server (the
   wrong authKey fails verification) before the client would even attempt
   to unwrap anything.
5. Client stores AK in local storage only (extension: IndexedDB `device`
   store; never uploaded, never sent anywhere else).
```

Argon2id parameters follow OWASP's 2023 minimum recommendation: `m=19456`
KiB, `t=2`, `p=1`, 32-byte output
(`extension/src/crypto/index.ts`/`web/src/crypto/index.ts`::`DEFAULT_KDF_PARAMS`).
They're stored per-account (`kdf_params`) rather than hardcoded server-side,
so a future account could use different cost — but every account created by
either client today uses this default, and changing what a specific
account's `kdfParams` says would change its derived `M` (and therefore
`authKey`/`KEK`), so it must never be edited for an existing account outside
of a full password change (§4), which picks a fresh salt anyway.

Clients do not trust whatever `kdfParams` and `kdfSalt` the server returns: a hostile server could otherwise hand back trivially cheap
parameters and make offline password guessing cheap. Both clients reject
`m` outside 19456–262144 KiB, `t` outside 2–10, `p` outside 1–4, any
non-integer value, and a salt shorter than 16 or longer than 64 bytes,
before deriving anything.

Because AK is generated once and merely re-wrapped afterward (never
re-derived from the password), **every device that successfully logs in
with the account password unwraps the identical AK** — there is no
device-to-device handshake, no "pending authorization" state, and no
plaintext key material ever crosses the server. Logging in on a second or
third device is sufficient to resume decrypting all synced data.

---

## 3. Adding a Device

There is no separate step: §2 already covers it. A new device registers
with the account's email + password like any other device, prelogin-fetches
the same `kdfSalt`/`kdfParams`, and unwraps the same AK on the spot. No
confirmation from an already-connected device is required or possible.

This trades the "explicit per-device trust decision" property of a
device-to-device key-grant scheme for operational simplicity: anyone who
knows the account password can decrypt the account's data on any device,
immediately. That is an explicit, deliberate design choice for this
project's threat model (a single self-hoster syncing their own devices) —
see §5 for what this implies about password strength and rotation.

## 4. Key Rotation

**SDEK rotation** introduces a new SDEK version without discarding old ones:

```text
old key (SDEK_v(n))
   -> new key (SDEK_v(n+1)) derived via HKDF(AK, info=...v(n+1))
   -> new operations encrypted with SDEK_v(n+1), tagged keyVersion=n+1
   -> existing operations/snapshots remain decryptable because SDEK_v(n)
      is still derivable from AK, which every authorized device still holds
```

**Password change** (`POST/PATCH /api/v1/auth/password`, web dashboard):
because the data key is not derived from the password, this does **not**
change what any device can decrypt. The client derives the old `authKey`/`KEK` (via a fresh
prelogin call) to unwrap the current AK, picks a *new* `kdfSalt`, derives a
*new* `authKey`/`KEK` from the new password, and re-wraps the *same* AK
under the new KEK. The request —
`{ currentAuthKey, newAuthKey, newKdfSalt, newKdfParams, newWrappedAK }` —
lets the server verify the old `authKey` and swap in the new fields in one
transaction, without ever re-encrypting any stored data: AK, and therefore
every `SDEK_v(N)` derived from it, is unchanged. Every device just needs to
sign in again with the new password to unwrap the same AK — no reconnect,
no data becomes unreadable. As part of the same call, the server also
revokes every other active web session for the account (a stolen session
cookie must not keep working after the password changes).

**Account key rotation** — generating a genuinely *new* AK — is a distinct,
more disruptive operation for when the old password (or a device) may be
compromised and the current AK itself can no longer be trusted: a password
change alone does not protect data from someone who already holds AK. This
would introduce a new `SDEK` root, require re-encrypting or re-uploading
data under a new `keyVersion`, and revoke every other device. **This is not
implemented yet** — there is no API for it today. Only ordinary password
change (which re-wraps the existing AK) is available.

**Salt rotation**: regenerating `kdf_salt` outside of a password change
would orphan the currently-wrapped AK (nothing could re-derive the KEK that
wrapped it), so this only ever happens as part of a full password change,
never on its own.

## 5. Missing Key / Recovery

There are two different reasons a device can fail to read a downloaded
operation, and they are handled in opposite ways.

**Authentication failure (skip).** If a device cannot decrypt an operation —
most commonly because it was encrypted under an AK it doesn't hold (e.g. it
was set up against a different account, or account key rotation — §4 — is
implemented in the future and this device hasn't picked up the new AK yet),
or because the ciphertext or its metadata was tampered with (§6, AAD) — that
single operation is logged (`console.warn("HelixSync: could not decrypt
operation, skipping", ...)`), marked applied, and skipped
(`extension/src/sync/engine.ts::decryptWithResolver`). Sync itself continues
normally: the download cursor still advances and every other operation in
the batch (and everything after it) is still applied.

This is a deliberate trade-off, not an oversight: the alternative —
leaving the operation unapplied and refusing to advance the cursor past it
— would block every operation after it, including new data, from ever
reaching that device again. Losing one object's history locally is preferable to
silently wedging sync forever.

**Reconnecting does not retroactively recover already-skipped data** on
that device — once an operation is marked applied, it's never re-attempted
even after a later reconnect with the correct password, since to this
device it looks identical to an operation it already successfully applied.
The data isn't gone from the server or from any other device that still
holds the correct key for it; it's specifically *this* device that gave up
on *that* operation. The server never sees the password or any key derived
from it in a recoverable form, never stores plaintext AK, and never assists
recovery of historical data encrypted under an AK no device can currently
unwrap. This is a deliberate consequence of true E2E encryption, not a bug.

**Unsupported envelope version (halt, do not skip).** An envelope whose `v`
the client does not understand (§6) is not corrupt — it was written by a
client speaking a different format, and this client simply cannot read it
*yet*. Skipping it would mark it applied and lose it for this device forever,
even after the user updates, so the engine does the opposite: it raises
`UnsupportedEnvelopeVersionError`, stops the sync cycle with an error status
("update the HelixSync extension"), leaves the operation unmarked and the
download cursor behind it, and retries on every later cycle. Everything
before the unreadable operation in the same page is applied and recorded
first; nothing at or after it is. A snapshot resync containing such an
envelope is refused before any local state is cleared or changed. Once the
extension is updated, the same operations are downloaded again and applied
normally.

This applies to every AAD-bound envelope: operation payloads, snapshot
objects, and each segment inside a bulk history container (§6.1).

## 6. Encryption Envelope

When `encryptionVersion >= 1`, an operation's `payload` field contains:

```json
{
  "v": 2,
  "keyVersion": 3,
  "alg": "xchacha20poly1305",
  "nonce": "base64url...",
  "ciphertext": "base64url..."
}
```

| Field        | Meaning                                                                 |
|--------------|--------------------------------------------------------------------------|
| `v`          | Envelope format version. **Currently `2`, and frozen** (see below). Independent of `encryptionVersion` on the operation, which is the coarse "is this encrypted at all" marker used by the server. |
| `keyVersion` | Which `SDEK_v(n)` was used.                                              |
| `alg`        | Algorithm identifier: `xchacha20poly1305`.                               |
| `nonce`      | 24-byte XChaCha20 nonce, base64url.                                      |
| `ciphertext` | Encrypted plaintext operation payload (the actual bookmark/history/tab fields) with the 16-byte Poly1305 tag appended, base64url. |

`protocolVersion`, `encryptionVersion`, and `keyVersion` together let any
future client determine exactly how to interpret a stored operation without
guessing.

The server stores `payload` as an opaque JSON/binary blob (Postgres
`jsonb`/`bytea`) and never attempts to interpret it when
`encryptionVersion >= 1`.

### 6.0 Associated data and the frozen version

Every envelope is bound to the operation's plaintext metadata through the
AEAD's associated data. The server stores `objectType`, `objectId` and
`operationType` next to the ciphertext, unauthenticated; without binding, a
malicious server could relabel an operation (a bookmark payload re-tagged as
a tab create, a create re-tagged as a delete) or splice a ciphertext onto
another object without invalidating its tag. The AAD is the UTF-8 JSON
encoding of the array

```json
["<objectType>", "<objectId>", "<operationType>"]
```

and decryption fails (authentication failure, §5) if any of the three
differs from what the encrypting device used. Bulk history segments use
`["historyVisit", <objectId of the bulkImport op>, "bulkImport"]`.

`v: 2` is this AAD-bound format, and the format is **frozen**: anything that
changes how an envelope is built or authenticated must take a new `v`.
Decryption accepts exactly `v: 2`. There is deliberately no fallback that
reads the earlier `v: 1` format (which had no AAD): any such path would
permanently allow relabeling of precisely those ciphertexts. A `v` other
than `2` — older or newer — raises the unsupported-version halt described in
§5, never a silent skip.

Do not confuse `v` here with the other version fields in the protocol: the
op-level `encryptionVersion` (marks "encrypted", nothing more), `keyVersion`
(selects the SDEK), the account-key wrap in §2 (its own `v`, which stays
`1`), and the `v`/`bulkVersion` fields of a bulk history container and its
segment plaintext (§6.1), which describe data layout, not encryption.

### 6.1 Segmented bulk envelope (historyVisit / bulkImport)

Single-operation history import (`docs/protocol.md` §8.3.1) carries N
individually-encrypted visit segments inside one op — same SDEK, same
`xchacha20poly1305`, no new cryptography. Two wire formats exist side by
side; `bulkVersion` on the stored op payload says which. v1 data is never
rewritten to v2 — both must stay decodable forever.

**`bulkVersion: 1`** — per-segment plaintext repeats the full `url`/`title`
on every visit:

```json
{ "v": 1, "visits": [{ "url": "...", "title": "...", "visitedAt": "..." }, ...] }
```

**`bulkVersion: 2`** — per-segment plaintext groups visits by URL (the
producer already has them grouped coming out of enumeration; v1 threw that
grouping away) and stores epoch-ms visit times instead of one ISO timestamp
string per visit. Field names are short (`u`/`t`/`v`) since this plaintext
may also be compressed (§6.2) before encryption, so per-field-name overhead
is paid either way:

```json
{ "v": 2, "groups": [{ "u": "...", "t": "...", "v": [1731000000000, ...] }, ...] }
```

~10k visits per segment, either format. Stored op payload:

```json
{
  "v": 1,
  "bulkVersion": 2,
  "codec": "deflate-raw",
  "visitCount": 123456,
  "segments": [{ "v": 2, "keyVersion": 3, "alg": "xchacha20poly1305", "nonce": "...", "ciphertext": "..." }, ...]
}
```

Here the container's `"v": 1` and `bulkVersion` describe how the container and
the segment plaintext are laid out; only each segment's own `"v"` is an
envelope version (§6.0). The container itself is not an envelope, so the
engine passes it to the history applier as-is after checking each segment's
`v`, and the segments are authenticated when they are expanded.

`codec` appears only on `bulkVersion: 2` containers, and only when the
producing device confirmed `CompressionStream("deflate-raw")` support
(§6.2 — feature-detected, never version-gated). Its absence means
uncompressed, not "unknown": a producer that can't confirm support omits
the field and ships an ordinary uncompressed v2 container rather than
failing the import over it.

Each element of `segments` is a standard §6 envelope (`v: 2`, own nonce, own
tag, bound by AAD to the bulk op's `objectId`) under the same SDEK/`keyVersion`. `visitCount` is a plaintext int (the
server counts it without decrypting); everything else stays opaque. Decrypt:
per-segment AEAD decrypt, then inflate if `codec` says to, then JSON-parse.
Segmentation bounds producer memory only — segments aren't globally sorted,
so a peer must decrypt (and, when compressed, inflate) every segment to find
the newest K visits.

### 6.2 Compression before encryption (`bulkVersion: 2`, `codec: "deflate-raw"`)

Bulk import segment plaintext is compressed with
`CompressionStream("deflate-raw")` before encryption, when the producing
device's runtime supports it. This is a deliberate, reviewed decision, not
an oversight, and it widens an existing information leak — recorded here
rather than left implicit.

**The leak.** Compressing before encrypting makes ciphertext length a
function of plaintext compressibility, so anyone who can observe a stored
envelope (the server, or anyone with server-level access) learns
approximately how repetitive the underlying browsing history is — heavy
revisit density (the same handful of URLs visited constantly) compresses
much further than a mostly-unique-URL history. This *widens* an existing
leak rather than introducing a new category of one: an envelope's
`ciphertext` length already correlates with total URL/title text volume
even without compression.

**Why this is not CRIME/BREACH-class.** Those attacks need an attacker who
can (a) inject or otherwise choose plaintext that gets compressed alongside
a secret in the same compression context, and (b) make many adaptive
observations of resulting ciphertext lengths to binary-search that secret
byte by byte. Neither condition holds for a one-shot history bulk import:
the compressed unit is the user's own browsing history, not a request
mixing attacker-controlled input with a secret, and there is no
repeated-adaptive-request oracle — an import's segments are produced once,
not regenerated against attacker-chosen variations.

**Accepted trade-off.** The leak this introduces is real but modest — a
quantitative widening of an already-present one — and the specific attack
class compress-before-encrypt is infamous for enabling does not apply to
this data flow. Weighed against the bandwidth/CPU this buys (most of a
~38x wire-size reduction on top of the §6.1 v2 grouped format), the
trade-off is judged worth it for this feature. Revisit if that changes —
e.g. if bulk import segments are ever mixed with attacker-influenced
content, or become observable adaptively many times against the same
underlying secret.

## 7. Server Enforcement

A server instance configuration flag `REQUIRE_ENCRYPTION` (**on by default**:
an unset or empty variable means `true`) causes the upload endpoint
(§10.2 of `docs/protocol.md`) to reject operations with
`encryptionVersion: 0`: they are returned in the upload response's `rejected`
list with reason `encryption_required` and are not stored. Only an explicit
`false` or `0` turns enforcement off, and any other unrecognised value fails
startup rather than being guessed at. In local testing or development
environments it can be set to `false` to permit plaintext payloads, but the
server then logs a startup warning
(`"HelixSync is running WITHOUT end-to-end encryption enforcement (REQUIRE_ENCRYPTION=false) — this deployment is NOT production-ready"`)
whenever `REQUIRE_ENCRYPTION=false`.

The same rule applies when the per-account `user_settings.require_encryption`
column is set (nothing in the API sets it today). `GET` and `PATCH
/api/v1/sync/settings` report the effective value, the server flag OR the
account column, as `requireEncryption`, which is what the dashboard's Security
page shows.

---

## 8. Limit: the Web Dashboard

The dashboard's code is served by your server. If that server is hacked,
the attacker can change the login page to steal the password you type, and
with it decrypt your data. The extension doesn't have this problem: its
code comes from the extension install, not the server.

Only use the dashboard on a server you trust.
